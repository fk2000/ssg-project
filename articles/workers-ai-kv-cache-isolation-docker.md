## はじめに

2026年10月26日、Cloudflare が Workers AI（Cloudflare のサーバーでAIモデルを動かすサービス）の不具合を公表しました。長いプロンプトへの回答に、**ほかの利用者のリクエストの中身が混ざることがあった**という内容です。

この記事では、まず公式の発表に書いてあることだけを整理します。そのうえで、インフラ担当として何を持ち帰るか、そして**手元の Docker で「送る前に伏せる」「返ってきたら中身を確かめる」を実際に動かした結果**を紹介します。

出典はすべて Cloudflare 公式ブログです。

- https://blog.cloudflare.com/kv-cache-exposure-remediation/

## なぜ起きたか（公式の説明の範囲で）

公式は「2つの問題が重なった」と説明しています。

### 1つ目：設定のずれ

GLM-5.3 は **1,048,576 トークン**のコンテキスト（一度に読めるプロンプトの長さ）で公開されていました。ところが、プロンプトを処理する GPU 側の KV キャッシュ（モデルが計算途中の結果をためておくメモリ領域）は **681,280 トークン分**しかありませんでした。

Cloudflare はこのずれを公開前に知っていました。ただ「入りきらないプロンプトはエンジンがエラーを返すはず」と考え、長いプロンプトのテストでも成功の応答が返ってきたため、問題ないと判断していたそうです。

### 2つ目：SGLang の不具合

SGLang（Cloudflare が使っているオープンソースの推論エンジン）は、プロンプトの処理（prefill）と回答の生成（decode）を別の GPU で分担する「分離構成」で動いていました。

入りきらないプロンプトは内部で「拒否」の印が付き、1トークンの仮の中身に差し替えられます。本来はここでエラーを返すべきでしたが、分離構成では「終わったかどうか」しか確かめておらず、拒否された事実が decode 側に伝わりませんでした。

その結果、decode 側は「長いプロンプトの分が書き込まれた」と思い込み、**前のリクエストが残したままのメモリ**を読んで回答を作りました。公式によれば、KV キャッシュのページは性能のためにリクエストごとにゼロで消していないそうです。

### 怖いのは「HTTP 200」で返ってきたこと

公式の説明で一番重いのはここだと思います。

> The client got HTTP 200 instead of HTTP 400.

本来は 400（リクエストの誤り）になるはずが、200（成功）で、しかも文章として自然な回答が返っていました。Cloudflare 自身も「テストでは HTTP のステータスと性能しか確かめておらず、出力の中身は確かめていなかった」と書いています。

### 対応

公式に書かれている主な対応です。

- KV キャッシュを約204万トークン分に広げ、コンテキストより大きくした
- 拒否されたリクエストを受け渡し前に止めるよう、エンジンを修正した
- SGLang を分離構成で使っている事業者には **v0.5.22 以降**への更新を勧めている

## インフラ担当としての教訓

ここからは筆者の考察です。

### 教訓1：HTTP 200 でも、中身は確かめる

監視やテストが「ステータスコードが 200 か」だけで終わっていないか、見直すきっかけになります。AIの応答は、形式が正しくても中身が正しいとは限りません。今回の件はまさに「200で自然な文章なのに、他人のデータ」でした。

自分のリクエストに目印（カナリア。本物のデータに混ぜておく見分け用の文字列）を入れて、返事に自分の目印だけがあるかを確かめる、という方法が手元でもできます。Cloudflare も修正の確認に canary-marker（目印）のテストを使ったと書いています。

### 教訓2：機密は外に送らない。送るなら伏せる

どれだけ大きな事業者でも、サービスの中の隔離（テナント分離）は崩れることがあります。利用者側でできるのは、**そもそも混ざって困るものを送らない**ことです。

- 個人情報やAPIキーは、送る前に伏せ字にする
- 伏せる処理そのものは、外とつながらない場所で動かす

### 教訓3：「上限は自分で測る」

公式の運用者向けの推奨の1つめは「KV プールの大きさとコンテキスト長を、エンジンの起動ログから測って比べる。エンジンが拒否してくれると思い込まない」でした。自分で SGLang などを動かす場合は、そのまま持ち帰れる教訓です。

## 手元でできる分離：Docker で試した最小例

ここからは筆者が実際に動かした結果です。

### 試した環境

- Linux（x86_64）、Docker Engine 29.9.1
- イメージ：`alpine:3.20`（中身は 3.20.10）
- 実行日：2026年10月27日

ローカルLLMそのものは重いので、今回は **「送る前の伏せ字コンテナ」** と **「返ってきた回答の検査コンテナ」** の2つだけを作りました。どちらも外のネットワークにつながらない設定で動かします。

### 手順1：伏せ字にするスクリプト

`mask.sh` を作ります。メールアドレス、APIキーらしい文字列、電話番号を伏せ字にします。

```sh:mask.sh
#!/bin/sh
# 標準入力の機密っぽい文字列を伏せ字にして標準出力へ
sed -E \
  -e 's/[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}/[EMAIL]/g' \
  -e 's/(sk|xai|ghp)[-_][A-Za-z0-9_-]{16,}/[API_KEY]/g' \
  -e 's/[0-9]{3}-[0-9]{4}-[0-9]{4}/[PHONE]/g'
```

試す入力 `sample.txt` です。キーは本物ではなく、ダミーの文字列です。

```text:sample.txt
問い合わせ: taro.yamada@example.com / 090-1234-5678
設定: XAI_API_KEY=xai-AAAABBBBCCCCDDDDEEEE1234
本文: ログインできないので見てください
```

### 手順2：ネットワークなしのコンテナで伏せる

`--network none`（ネットワークを付けない）と `--read-only`（ファイルを書き換えられない）を付けて動かします。

```bash
chmod +x mask.sh
docker run --rm -i --network none --read-only \
  -v "$PWD/mask.sh:/mask.sh:ro" alpine:3.20 /mask.sh < sample.txt
```

結果です。

```text
問い合わせ: [EMAIL] / [PHONE]
設定: XAI_API_KEY=[API_KEY]
本文: ログインできないので見てください
```

キー名（`XAI_API_KEY`）は残り、値だけが伏せられました。外に送るのは、この伏せた後の文章だけにします。

### 手順3：本当に外とつながらないか確かめる

```bash
docker run --rm --network none alpine:3.20 wget -q -T 3 -O- https://example.com
echo "exit=$?"
docker run --rm --network none alpine:3.20 ip -o link
```

結果です。

```text
wget: bad address 'example.com'
exit=1
1: lo: ...
```

名前解決（ドメイン名からIPアドレスを調べること）すらできず、使えるネットワークは `lo`（自分自身との通信用）だけでした。伏せる前の生データを持つコンテナが、外へ何かを送ってしまう経路はありません。

また `--read-only` で書き込みもできないことを確かめました。

```bash
docker run --rm --read-only alpine:3.20 touch /tmp/x
```

```text
touch: /tmp/x: Read-only file system
```

### 手順4：返ってきた回答を目印で検査する

教訓1の「200でも中身を確かめる」を、最小の形で作りました。`check.sh` は、自分の目印があり、ほかの目印（`CANARY-` で始まる別の文字列）が無いときだけ OK にします。

```sh:check.sh
#!/bin/sh
# 使い方: check.sh 自分のカナリア < 応答ファイル
# 応答に「自分の目印」があり、「他の目印(CANARY-*)」が無ければ OK
mine="$1"; body=$(cat)
echo "$body" | grep -q "$mine" || { echo "NG: 自分の目印がない"; exit 2; }
other=$(echo "$body" | grep -oE 'CANARY-[A-Z0-9]+' | grep -v "^$mine$" | sort -u)
[ -n "$other" ] && { echo "NG: 他の目印が混入: $other"; exit 3; }
echo "OK"
```

正常な応答（`ok.txt`）と、別の目印が混ざった応答（`mixed.txt`）を用意しました。どちらも手で作った例です。

```text:ok.txt
要約: ログイン不具合の相談です。(CANARY-A1B2)
```

```text:mixed.txt
要約: ログイン不具合の相談です。(CANARY-A1B2)
別件: 請求書の件 (CANARY-Z9Y8)
```

```bash
chmod +x check.sh
for f in ok.txt mixed.txt; do
  docker run --rm -i --network none --read-only \
    -v "$PWD/check.sh:/check.sh:ro" alpine:3.20 /check.sh CANARY-A1B2 < "$f"
  echo "exit=$?"
done
```

結果です。

```text
OK
exit=0
NG: 他の目印が混入: CANARY-Z9Y8
exit=3
```

終了コード（コマンドの成否を表す数字）が 0 以外なら止める、という形にしておけば、CI（自動テストの仕組み）や監視にそのまま組み込めます。

### この例の限界

正直に書いておきます。

- 伏せ字は正規表現（文字の並びのパターン）なので、形が違う機密は見逃します。完全な対策ではありません。
- 目印の検査で見つけられるのは「目印付きのデータ」が混ざった場合だけです。今回の Workers AI の件のように、他人の目印の無いデータが混ざった場合は検出できません。それでも、自分の目印が消えている・返答が明らかに別件、といった異常に気づく足がかりにはなります。
- 一番確実なのは、機密を含む処理をローカルLLM（自分のマシンで動かすAIモデル）など手元で完結させることです。

## まとめ

- Workers AI の GLM-5.3 で、長いプロンプトへの回答155件に他の利用者のデータが混ざりました（2026年8月27日〜9月9日、公式発表）。
- 原因は、設定のずれと SGLang の不具合の重なりで、エラーになるべきものが **HTTP 200** で返っていました。
- 利用者側の対策は「送る前に伏せる」「伏せる場所は外とつながない」「返ってきた中身を確かめる」。Docker の `--network none` と `--read-only` で最小の形を作れます。
