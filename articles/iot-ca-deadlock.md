## はじめに

2026年10月21日（UTC）、PHPの緊急セキュリティリリース（PHP 8.5.12 / 8.4.27 / 8.3.36 / 8.2.35）が公開されました。認証なしでリモートコード実行につながる2件の脆弱性（CVE-2026-109618、CVE-2026-109619）を修正するもので、米CISAもすぐにパッチを当てるよう呼びかけています。Webの現場は、いままさにバージョンアップに追われています。

もちろん、この対応は最優先です。ただ、Webの脆弱性には**「パッチを当てて、再起動・デプロイすれば直る」**という出口があります。

一方で、技術の裏側には出口がもっと遠い問題があります。それが**組み込み・IoT機器での認証局（CA）の失効・移行トラブル**です。

「証明書を更新する」「ルートを切り替える」と書けば同じ作業に見えます。しかしWebと組み込みとでは、その作業の重さがまったく違います。この記事では、組み込みでCAの問題が積み上がる構造的な理由と、設計でできる対策を整理します。

---

## 1. Webと組み込みでは「CAの変更」の前提が違う

### Webシステム（サーバー／ブラウザ）

- OSやブラウザが持つ**ルート証明書ストアは、自動アップデートで常に更新**されます。
- 中間証明書の失効やルートの切り替えがあっても、**サーバー側で証明書や中間証明書を差し替えれば、ほぼすぐに復旧**できます。
- 更新はACMEなどで自動化されているのが当たり前になりつつあります。

### 組み込みシステム／IoT機器

- ファームウェアの中に、**特定のルート証明書や中間証明書が埋め込まれている（固定されている）**ことがよくあります。
- 信頼しているCAの証明書が期限切れになる、失効する、または接続先のサーバーが別のCAの証明書に切り替わる。すると機器は**「通信相手を信用できない」と判断し、その相手とのTLS通信が止まります**。
- 証明書ストアを更新する手段は、多くの場合**ファームウェア更新しかありません**。

ポイントは、**Webでは「信頼の起点（トラストストア）」を誰かが更新し続けてくれるのに、組み込みでは出荷した時点で止まりがち**だということです。

---

## 2. 組み込みで問題が積み上がる4つの構造的要因

### ① OTA（遠隔アップデート）そのものが通らない ― デッドロック

いちばん怖いのがこのパターンです。

ファームウェアを配るためのOTA通信も、TLS/HTTPSで守られています。そのため、CAの検証に失敗すると、**「直すためのパッチを配る通信すら通らない」**という鶏と卵の状態になります。

こうなると、残る手段は物理的なものだけです。

- 現場への作業員の派遣
- 筐体を開けて、JTAG/UARTで手作業で書き換える
- 最悪の場合は、機器の回収・交換

**管理画面には「オフライン」の機器がずらりと並び、ログも取れず、リモートからは何もできない**。手元にあるのは、出荷台数と設置場所のリストだけです。障害の原因が分かっていても、**直すための道そのものが閉じている**。これが「詰む」ということです。

### ② セキュアブートやハードウェアの Root of Trust は、変えにくい

近年はセキュリティを強めるために、TPMやセキュアエレメントの中にCA証明書や公開鍵のハッシュを書き込む設計が増えています。

これは改ざんに強い反面、**CA側の都合による想定外の失効や移行に、ハードウェアの段階で対応できない**ことがあります。守りを固めるほど、緊急時の逃げ道も減るというジレンマです。

### ③ 現場の機器は長く使われる

Webでは数年ごとに作り直すのが普通ですが、産業機器、スマートメーター、車載ECU、医療機器などは、**Webのシステムよりずっと長く動き続けることがよくあります**。

その長い運用の間に、次のようなことが起こり得ます。

- ルート証明書や中間証明書の期限切れ
- 暗号・署名アルゴリズムの世代交代（例：SHA-1からSHA-256へ）
- CA事業の譲渡や終了、ブラウザ・OSからの信頼の取り消し

### ④ 証明書の短寿命化と、IoTの運用の現実がかみ合わない

2025年、CA/Browser Forum は**Ballot SC-081**で、公開TLSサーバー証明書の有効期間の上限を段階的に短くすることを決めました。

| 発行日 | 有効期間の上限 |
| --- | --- |
| 2026年3月15日より前 | 398日 |
| 2026年3月15日以降 | **200日** |
| 2027年3月15日以降 | **100日** |
| 2029年3月15日以降 | **47日** |

Let's Encrypt もこの流れに沿っています。

- 2026年5月13日からは、**45日の証明書**を `tlsserver` プロファイルで希望者向けに発行しています。
- 2026年1月に、**有効期間が約6日（160時間）の短寿命証明書**を一般提供しました（希望者のみ）。
- 標準の証明書は90日から、**2027年2月に64日、2028年2月に45日**へ短くなる予定です。

Webサーバーにとっては、ACMEで自動更新していれば大きな問題ではありません。しかし、IoTの現場から見ると話が違います。

- **機器がつなぐクラウド側のサーバー証明書が、年に何度も入れ替わります。** 機器側が「特定のサーバー証明書や中間証明書」を固定（ピンニング）していると、入れ替わるたびに通信が止まるおそれがあります。
- 機器が**自分で証明書を更新する**設計の場合、電池で動き、通信回数を極限まで減らしているデバイスには、頻繁な更新処理は通信量と電力の負担になります。
- 長期間オフラインの機器（倉庫で在庫として眠っていた機器など）は、**電源を入れた時点で、すでに手持ちの情報が古くなっている**ことがあります。

:::message
SC-081 が対象にしているのは**ブラウザが信頼する公開TLSサーバー証明書**です。機器のクライアント証明書を自前のプライベートCAで発行している場合は、この上限の対象外です。それでも、機器がつなぐ先のサーバー証明書は公開CAのものであることが多いので、**間接的に影響を受けることが多いです**。
:::

## 3. 実例：2021年、DST Root CA X3 の期限切れ

これは想像上の話ではありません。

2021年9月30日、Let's Encrypt の証明書チェーンで使われていた**ルート証明書「DST Root CA X3」の有効期限が切れました**。Let's Encrypt は自前のルート「ISRG Root X1」へ移行していましたが、**ISRG Root X1 をトラストストアに持たない古い端末やソフトウェア**では、Let's Encrypt の証明書を使ったサイトやAPIにつながらなくなる問題が起きました。

- 更新が止まった古いOS（例：ISRG Root X1 を持たない古いiOSやmacOS）。なお古いAndroidは、Let's Encrypt が用意したクロス署名のチェーンによって、多くがつながり続けました。
- 古いOpenSSLを使っているシステムでは、チェーンの検証の仕方によって、新しいルートがあっても失敗する場合がありました。
- ルート証明書を更新する手段がない組み込み機器

Webのサーバー側は証明書チェーンを調整すれば済みました。しかし**クライアント側の機器は、多くの場合ファームウェアを更新しないと直りません**。これこそが、本記事で言いたい「Webと組み込みの断絶」です。

## 4. 考察：これからの組み込みに必要な設計の転換

セキュリティを固めるほど、運用の柔軟さは失われます。このジレンマから抜けるには、**「CAはいつか変わる・失効する」ことを前提に、最初から設計しておく**ことが近道です。

### ① 予備のCA・ルートを複数持つ

- 1つのCAに頼らず、**複数のルート証明書をあらかじめ入れておきます**。
- プライマリのCAで検証に失敗したら、**セカンダリのCAで通信を試みる**冗長構成にします。
- 証明書を固定するなら、末端のサーバー証明書ではなく、**ルートや複数の公開鍵に固定**して、入れ替わりに耐えられるようにします。

### ② 独立した「OTAレスキューモード」を持つ

- 通常のアプリ通信とは切り離した、**復旧専用の通信経路とモード**を用意します。
- 信頼の起点も、通常の経路とは別に持たせます（例：自社で管理する長期のルートで、ファームウェアの署名を検証する）。
- ここで大事なのは、**レスキューの経路そのものが、新たな攻撃の入口にならない**ようにすることです。

### ③ 証明書の自動更新プロトコルを組み込む

- **EST（RFC 7030）、SCEP（RFC 8894）、ACME（RFC 8555）**などを使い、機器が自分で安全に証明書を更新し続けられるようにします。
- **トラストストア（ルート証明書の一覧）もファームウェアとは別に更新できる**ようにしておくと、ファーム全体の更新に頼らずに済みます。

### ④ 運用で「期限」を見えるようにする

- 出荷済みの機器が、**どのルートを信頼し、どの証明書がいつ切れるか**を台帳で管理します。
- CAや業界団体の発表（SC-081 のようなもの）を、**製品のロードマップに組み込んで**追いかけます。

---

## まとめ

- PHPの脆弱性のように、Webの問題は**「パッチを当てて再起動・デプロイ」**で直せます。
- 組み込み・IoTでCAが失効・移行すると、**OTAすら通らないデッドロック**に陥ることがあり、**現地対応や回収という物理的なコスト**につながります。
- 証明書の短寿命化（200日→100日→47日）は、Webの安全には効く一方で、**長く動き、通信の少ない機器の運用とは大きくずれています**。
- これからのIoT製品の成否は、**「CAは変わる」前提の設計を、最初の段階からどれだけ盛り込めるか**にかかっています。

:::message
PHPのパッチ対応が落ち着いたら、出荷済みの機器が「どのルートを信じているか」を一度棚卸ししておくことをおすすめします。
:::
